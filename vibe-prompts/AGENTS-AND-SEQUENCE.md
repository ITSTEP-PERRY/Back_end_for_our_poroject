# Сколько агентов и в каком порядке вайбкодить

[← Оглавление](./README.md) · [PITFALLS](./PITFALLS.md) · [Запуск скрипта](./HOW-TO-RUN-SEQUENCE.md)

Документ отвечает на два вопроса:

1. **Скольким агентам** разумно раздать этот набор промптов.  
2. **В какой последовательности** их выполнять, чтобы не сломать стыки.

---

## Короткий ответ

| Режим | Агентов | Когда |
|-------|---------|--------|
| Соло | **1** | Учишься / один ноут / первый проход `00→12` |
| Пара | **2** | Backend + Frontend параллельно после скелета API |
| Команда | **3** | Backend · Desktop · Mobile (как зоны ITSTEP) |
| Максимум | **4** | + отдельный агент на Auth-стык / админку / polish |
| Не надо | **5+** | Конфликты в git, разные контракты API, хаос в JWT/корзине |

> Набор промптов рассчитан на **1–3 агента**. Четвёртый — только на узкую задачу.  
> Раздавать все 00–12 сразу пятерым агентам — плохая идея.

---

## Рекомендуемые роли агентов

### Вариант A — один агент (по умолчанию)

Один чат (или серия чатов) идёт строго по номерам:

`PITFALLS` → `00` → `01` → … → `12`

Между крупными блоками можно **новый чат**, но с кратким контекстом:

```text
Проект Perry. Уже сделано: шаги 00–05 (API + JWT).
Сейчас выполняем промпт из vibe-prompts/06-desktop-vite.md.
Правила: vibe-prompts/README.md + PITFALLS.md.
```

### Вариант B — два агента

| Агент | Зона | Промпты | Старт после |
|-------|------|---------|-------------|
| **BE** | Product API | `01` `02` `03` `04` `05` `11`(seed) | сразу после `00` |
| **FE** | Desktop (+ позже admin UI) | `06` `07` `08` `10` | когда есть `/api/health` + `/api/products` |

Общий контракт (оба читают): [PITFALLS](./PITFALLS.md), [05](./05-auth-jwt-bridge.md).

Mobile (`09`) — либо тот же FE после desktop MVP, либо третий агент.

### Вариант C — три агента (как команда Perry)

| Агент | Аналог в команде | Промпты |
|-------|------------------|---------|
| **Agent-BE** | Сергей / Product API | `01–05`, частично `11`, `12` (backend smoke) |
| **Agent-Web** | Яна / Desktop | `06–08`, `10`, `07` критичен |
| **Agent-Mobile** | Илона / Expo | `09`, куски `10`/`07` (тот же Auth-контракт) |

**Не отдавать Mobile агенту свой Auth и свой Product API** — только клиент к уже согласованным URL/JWT.

Auth Service (Влад) в этот набор **не входит** как «напиши Auth с нуля».  
Агентам: только [05](./05-auth-jwt-bridge.md) + [07](./07-desktop-auth-ui.md) как **потребители** внешнего Auth.

### Вариант D — четыре агента (осторожно)

Добавь **Agent-Polish** или **Agent-Admin**:

- только [08](./08-admin-panel.md) + [10](./10-figma-polish.md) + [PITFALLS](./PITFALLS.md),  
- или только seed/медиа [11](./11-seed-media-run.md),

и только когда `main` API + базовый storefront уже в одной ветке/репо.

## Что можно параллелить, а что нельзя

```text
00 Vision                    ← всегда первым (или один раз на всех)
        │
        ▼
01 Backend skeleton          ← BLOCKER для всех остальных
        │
        ├──────────────┬─────────────────�          ← BLOCKER для всех остальных
        │
        ├──────────────┬─────────────────┐
        ▼              ▼                 ▼
02 Catalog       (ждать products)   (ждать products)
03 Cart          06 Desktop Vite     09 Mobile (позже)
04 Reviews       07 Auth UI          07-контракт тот же
05 JWT bridge    08 Admin
        │              │
        └──────┬───────┘
               ▼
        10 Figma polish (после рабочих экранов)
               ▼
        11 Seed / media (можно чуть раньше на BE)
               ▼
        12 Smoke (все вместе)
```

| Можно параллельно | Нельзя параллельно |
|-------------------|--------------------|
| `02` catalog + черновик `06` home (с mock) | `07` register до понимания контракта `05` |
| `08` admin UI после Admin JWT | Два агента правят одну `AuthClaims` / один `client.ts` вслепую |
| `09` mobile после стабильного API list/detail | Переписывать Auth Service «с нуля» рядом с Product |
| `11` seed на BE пока FE делает shell | Три агента меняют модель Product без договорённости |

## Последовательность для вайбкодинга (чеклист)

### Фаза 0 — подготовка (человек, 10–15 мин)

- [ ] Прочитать [PITFALLS.md](./PITFALLS.md)
- [ ] Решить: 1 / 2 / 3 агента
- [ ] Один репозиторий, одна ветка на фазу (или чёткие папки `src/` `frontend/` `mobile/`)
- [ ] В каждый чат вставить [правила стека](./README.md#правила-стека-копируй-в-чат)

### Фаза 1 — фундамент (строго последовательно)

1. [00-vision.md](./00-vision.md)  
2. [01-backend-skeleton.md](./01-backend-skeleton.md) → проверить `:5272/swagger` и `/api/health`  
3. [05-auth-jwt-bridge.md](./05-auth-jwt-bridge.md) *можно сразу после 01*, до красивого каталога — JWT понадобится рано  
4. [02-catalog-pdp.md](./02-catalog-pdp.md)

**Критерий выхода:** `GET /api/products` отдаёт items.

### Фаза 2 — ядро бэкенда (1 агент BE)

5. [03-cart-checkout-orders.md](./03-cart-checkout-orders.md)  
6. [04-reviews-wishlist.md](./04-reviews-wishlist.md)  
7. Вставить [промпт-предохранитель](./PITFALLS.md#промпт-предохранитель-для-ии)

**Критерий выхода:** checkout + review под User JWT; AuthorName не GUID.

### Фаза 3 — клиенты (параллель ок)

| Порядок Web | Порядок Mobile |
|-------------|----------------|
| [06](./06-desktop-vite.md) | дождаться products API |
| [07](./07-desktop-auth-ui.md) + PITFALLS Auth | [09](./09-mobile-expo.md) (после 06 или параллельно с 07) |
| [08](./08-admin-panel.md) | DEV Admin тот же Guid |

**Критерий выхода:** login/register multi-step на web; mobile каталог + login.

### Фаза 4 — полировка и демо

8. [10-figma-polish.md](./10-figma-polish.md) (+ снова Design из PITFALLS)  
9. [11-seed-media-run.md](./11-seed-media-run.md)  
10. [12-smoke-and-defense.md](./12-smoke-and-defense.md) — **один** агент или человек гоняет чеклист по всем частям

### Про one-shot (`99`)

- [99-one-shot-full.md](./99-one-shot-full.md) — **только одному** агенту.  
- Не раздавать 99 трём агентам сразу.  
- После первого milestone из 99 лучше перейти на шаги `02+`.

## Как формулировать задачу агенту (шаблон)

```text
Роль: Agent-BE | Agent-Web | Agent-Mobile
Репо: Perry (монорепо)
Сейчас выполняешь ТОЛЬКО файл: vibe-prompts/0X-....md
Обязательно соблюдай: vibe-prompts/PITFALLS.md и правила из vibe-prompts/README.md
Не трогай чужие зоны: [перечисли: mobile/ / admin / Auth Service]
Definition of Done: [1–3 пункта из критерия выхода фазы]
```

## Анти-паттерны

1. **Пять агентов × один промпт 99** — получите три несовместимых JWT и две схемы Product.  
2. **Mobile до `/api/products`** — агент нарисует UI на моках и потом всё переломает.  
3. **Register «в одном POST»** вопреки [07](./07-desktop-auth-ui.md) — аккаунты не создаются.  
4. **Разный DEV Admin Guid** на web и phone — «корзина не та».  
5. **Молчаливый rebase** чужих папок без review контракта API.

## Связь с реальной командой ITSTEP

| Зона | Промпты | Не отдавать |
|------|---------|-------------|
| Product API | 01–05, 11–12 | писать Auth Service |
| Desktop FE | 06–08, 10 | менять схему БД в одиночку |
| Mobile | 09 (+ контракт 07/05) | админку Users |
| Auth (Влад) | вне набора; только читать swagger | — |

Этот набор — **гайд потребителя Auth + владельца Product/FE/Mobile**, не замена Backend-client.

---

## Итоговая рекомендация

- **Учишься вайбкодить один** → 1 агент, последовательность `PITFALLS → 00…12`.  
- **Хочешь скорость как у команды** → 3 агента (BE / Web / Mobile) после зелёного `01+02`.  
- **Четвёртый агент** — только polish/admin/seed, когда контракты уже стабильны.  
- Всегда держи открытым [PITFALLS.md](./PITFALLS.md).
