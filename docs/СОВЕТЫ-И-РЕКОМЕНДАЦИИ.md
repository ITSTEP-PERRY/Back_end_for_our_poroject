## 1. Общая оценка

| Критерий | Оценка |
|----------|--------|
| Макеты auth (Login, Register, Verify, Forgot, Reset, Finishing, Success) | Хорошо для демо |
| Учебный / командный бэкенд (Razor + API + LocalDB) | Достаточно к защите зоны товаров |
| Production-ready auth и каталог | Ещё рано — и это нормально |

**Правило:** до защиты — «работает и объясняется»; после — «как в проде».

## 2. До защиты (добить)

Приоритет сверху вниз.

### 2.1. Стабильный демо-сценарий

Один прогон без сюрпризов на ноутбуке защиты:

1. Register → Finishing touches → Congratulations → витрина  
2. Logout / Login  
3. Forgot password → Reset → Log in новым паролем  
4. (Опционально) 3 неверных пароля → VerifyCode → вход  

Заранее завести тестовый email в БД и знать пароль.

### 2.2. Документация в GitHub

Всё важное должно открываться из репозитория, не с локального диска:

- `docs/ВОССТАНОВЛЕНИЕ-ПАРОЛЯ.md` + скрины `19–25`  
- `docs/КАТЕГОРИИ.md`, `КАТАЛОГ-ТОВАРОВ-АРХИТЕКТУРА.md` (если ещё не запушены)  
- актуальный README со ссылками  

Репозитории команды / личный: по договорённости (например My_Amazon2 и Back_end_for_our_poroject).

### 2.3. Речь на ~1 минуту про «дыры» демо

Честно и коротко:

> Сейчас SMTP в режиме stub: письмо пишется в лог, сброс пароля и код подтверждения удобно тестировать локально. Токен и код живут в памяти процесса (TTL). В продакшене — реальная почта и хранение в БД или Redis.

Так комиссия видит осознанность, а не «забыли безопасность».

### 2.4. Зона товаров на экране

Не только auth:

- витрина `/`, каталог `/Products`, карточка, корзина, заказ;  
- админ: `Admin` / `Admin` → категории / товары.  

Иначе диплом выглядит как «только формы входа».

### 2.5. Скриншоты в README

Login / Register / Verify / Forgot / Reset / Success — чтобы листать GitHub без запуска приложения.

## 3. На потом (не блокирует защиту)

### Auth и почта

1. **Реальный Gmail SMTP** — `Smtp:UseStub: false` + App Password; письмо со ссылкой Reset **без** авто-редиректа на Reset.  
2. **Токены и коды в БД / Redis** — переживают рестарт `dotnet run`.  
3. **Безопасный Forgot** — не светить «email не найден» (одно нейтральное сообщение).  
4. **Forgot → код на email → Reset** — если захотите тот же UX, что VerifyCode; сейчас токен в URL для демо достаточен.

### Каталог

5. **Миграция на Product + Variants + словарь атрибутов** — см. [КАТАЛОГ-ТОВАРОВ-АРХИТЕКТУРА.md](./КАТАЛОГ-ТОВАРОВ-АРХИТЕКТУРА.md). Большой отдельный этап.  
6. **Ядро схемы раньше фронта, детали атрибутов — после макетов PDP/фильтров** — не ждать весь React, чтобы начать БД; уточнять фильтры, когда будут экраны от команды.

### Платформа

7. JWT / нормальный API-auth для React.  
8. Полнотекстовый поиск (Elasticsearch и т.п.).  
9. Полировка фильтров и контракта под perry-front.

## 4. Если успеете только один техдолг сверх стабильного демо

| Выбор | Зачем |
|-------|--------|
| **1-й приоритет:** запушить доки + скрины | Комиссия и команда видят работу без вашего ПК |
| **2-й:** реальный SMTP | Звучит убедительнее на вопросах «а письмо?» |

Остальное спокойно в «потом».

---

## 5. Как не путать потоки auth (для защиты)

| Поток | Когда | Зачем |
|-------|--------|--------|
| **Login** | Обычный вход | Сессия |
| **VerifyCode** | 3 неудачных Login | Подтвердить email кодом и **войти** |
| **Forgot → Reset** | «Forgot password?» | **Сменить пароль** без старого |
| **Register → Finishing → Success** | Новая учётная запись | Имя/фамилия + вход |

На защите полезно сказать одной фразой: «VerifyCode — про вход после ошибок; Forgot — про смену пароля; Finishing — про регистрацию».

---

## 6. Каталог: порядок работ (рекомендация)

1. Зафиксировать **дизайн** (уже есть документ).  
2. Не ждать весь фронт, чтобы утвердить **Product + Variant + AttributeDefinition**.  
3. Детали набора характеристик под категорию — когда появятся макеты каталога и PDP.  
4. Реализацию миграций EF делать отдельным спринтом, не вперемешку с auth за ночь до защиты.
