# Оптимізація ресурсів Perry — етап 7

**Дата вимірювань:** 10.11.2026. **Джерело:** Prometheus, локальний кластер `docker-desktop`, namespace `perry-stage7`.

## Заявлені Requests / Limits

| Контейнер | CPU request | CPU limit | RAM request | RAM limit |
|---|---:|---:|---:|---:|
| API | 100m | 1000m | 256Mi | 768Mi |
| Frontend | 25m | 250m | 32Mi | 128Mi |
| PostgreSQL | 100m | 500m | 128Mi | 512Mi |

У всіх трьох компонентів налаштовані readiness і liveness probes.

## Фактичні вимірювання

| Компонент | Поточний CPU 10.11 | Поточна RAM | Пік CPU за попередні 24 год | Пік RAM за попередні 24 год |
|---|---:|---:|---:|---:|
| API | 0.53m | 80.27MiB | 57.16m | 80.57MiB |
| Frontend | 0.06m | 10.93MiB | 0.06m | 11.18MiB |
| PostgreSQL | 14.66m | 43.56MiB | 16.10m | 43.98MiB |

**Метод:** PromQL `rate(container_cpu_usage_seconds_total[5m])`, `container_memory_working_set_bytes`, та `max_over_time(...[24h:5m])`. Ці показники є спостереженням за доступною навантаженістю, а не синтетичним стрес-тестом; 24-годинний пік залежить від наявності метрик і scrape coverage.

## Контейнерні образи

Локальний .NET 10 кандидат: AMD64 приблизно **103 MB**, ARM64 приблизно **99 MB**. Обидва зібрано та скановано. **Порівняння з початковим образом у тих самих умовах не зафіксовано**; не стверджувати відсоток економії.

## Висновки й наступні дії

- CPU/RAM при виміряному навантаженні нижчі від Requests; це **не підстава** автоматично зменшувати ліміти.
- Зібрати базову/пікову статистику за реалістичного навантаження (одночасні запити, файли, запити БД), час відповіді, помилки, рестарти, OOM/evictions.
- Провести контрольне порівняння до/після при однаковій методиці.
- `metrics-server` відсутній, тож `kubectl top` недоступний. Для цього звіту метрики одержано з Prometheus.
- Перевірити обсяг логів і retention Loki/Prometheus, щоб уникнути зростання дискового навантаження.

**Статус оптимізації:** Requests/Limits налаштовано, фактичні вимірювання проведено, але навантажувальний тест і обґрунтування фінального tuning ще потрібні.
