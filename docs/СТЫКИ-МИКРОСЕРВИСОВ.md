## 1. Какая у нас архитектура (коротко)

Perry — **не один монолит**, а несколько сервисов + фронт:

```text
┌─────────────────┐     login / me / users      ┌──────────────────────────┐
│  perry-front    │ ──────────────────────────► │  Auth Service (Влад)      │
│  :3000          │                             │  Backend-client           │
│                 │     Bearer access JWT       │  Azure Container Apps     │
│                 │ ──────────────────────────► │                          │
│                 │     catalog / cart / …      └────────────┬─────────────┘
│                 │ ──────────────────────────►              │ Internal JWT
└─────────────────┘                             ┌────────────▼─────────────┐
                                                │  Product API (мы)         │
        (опционально admin users)               │  Back_end_for_our_poroject│
                ┌─────────────────┐             │  :5272 локально           │
                │ perry-admin-    │             │  каталог, корзина, заказы,│
                │ service / front │             │  reviews, wishlist        │
                └─────────────────┘             └──────────────────────────┘
```

| Сервис | Репо | Отвечает за |
|--------|------|-------------|
| **Auth** | [Backend-client](https://github.com/ITSTEP-PERRY/Backend-client) | регистрация, login, JWT, users, роли |
| **Product** | [Back_end_for_our_poroject](https://github.com/ITSTEP-PERRY/Back_end_for_our_poroject) | товары, корзина, заказы, отзывы, wishlist |
| **Front** | [perry-front](https://github.com/ITSTEP-PERRY/perry-front) | UI; логин → Auth, данные витрины → Product |
| **Admin users** | perry-admin-service / perry-admin-front | админ-управление пользователями (не Product DB) |

**Правило домена:** пользователи живут только в Auth. В Product в заказах / wishlist / отзывах — только `Guid UserId` из JWT, **без таблицы Users** (#94).

## 2. Какие были (и остаются) проблемы на стыках

Ниже — именно **межсервисные** проблемы, не «баги UI».

### Проблема A — Product хранил Users сам (сломана граница доменов)

**Симптом:** два источника правды о пользователе; Product не мог спокойно доверять Auth.  
**Риск:** рассинхрон ролей/статусов, дубли аккаунтов, сложный merge.

### Проблема B — Front логинился «не туда» / create review бил не в тот API

**Симптом:** витрина ходила в локальный Product `/api/auth` или в несуществующий `POST /api/products/{id}/reviews`.  
**Риск:** 404, пустые отзывы, ощущение что «сервисы не дружат».

### Проблема C — Product не умел проверять настоящий JWT Auth (#95)

**Симптом:** либо `SkipSignatureValidation`, либо свой локальный issuer — чужой access token от Auth не принимался / принимался небезопасно.  
**Риск:** 401 на wishlist/orders/reviews **или** дыра в безопасности.

### Проблема D — неизвестный / неподтверждённый контракт JWT (#96, #98)

**Симптом:** в Product зашиты ожидания:

| Параметр | Что ждёт Product сейчас |
|----------|-------------------------|
| Подпись | HS256, общий `Jwt:SigningSecret` |
| `iss` | `Perry.AuthService` |
| `aud` | `Perry.Client` |
| UserId | claim `sub` / `nameid` / `userId` (Guid) |
| Role | claim `role` = `User` \| `Admin` |
| Имя / email | claims `name`, `email` (желательно) |

Пока **живой payload** access token не сверили глазами, остаётся риск: «логин на Auth ок → Product 401 из‑за iss/aud» или «отзыв без AuthorName / без роли Admin».

### Проблема E — service-to-service (Internal) без plaintext credential (#97)

**Симптом:** Auth документирует Internal API (`GET /internal/users/{id}`), у команды в конфиге есть `local-service` + **CredentialHash**, но Product’у нужен **plaintext credential**, чтобы вызвать:

`POST /internal/auth/token` → `{ serviceName, credential }` → Internal JWT → `GET /internal/users/{id}`.

**Риск:** admin-orders / отображение имени покупателя по чужому `UserId` без Internal lookup неполное; нельзя официально ходить Auth↔Product backend-to-backend.

### Проблема F — отзывы не были привязаны к Auth UserId (#99–#104)

**Симптом:** FE бил неверный URL create; BE брал `NameIdentifier` вместо `AuthClaims`; не было unique `(UserId, ProductId)` и `GET /reviews/me`.  
**Риск:** «отзывы ничьи», дубли, кабинет «Мои отзывы» невозможен.

## 3. Что уже сделано (как решили)

### ✅ #94 — граница доменов

- Из Product API убраны таблицы `Users` / связанные FK.
- В `Orders`, `Wishlist`, `ProductReviews` остаётся только `UserId` (Guid из JWT).
- Login / register / admin-users — **только Auth Service**.

### ✅ #95 — подпись access JWT

- Получен общий **HS256** `Jwt:SigningSecret` от Auth.
- Секрет лежит в локальном **`.env`** Product (gitignored), не в репозитории.
- `SkipSignatureValidation = false` по умолчанию.
- В коде: `AddJwtAuthentication` + конфиг `Jwt:Issuer` / `Jwt:Audience` / `RoleClaimType=role` / `NameClaimType=sub` / `MapInboundClaims=false`.
- Docs: [ИЗМЕНЕНИЯ-2026-09-28-auth-95.md](./ИЗМЕНЕНИЯ-2026-09-28-auth-95.md) · Trello [#95](https://trello.com/c/T28F0b7e) → **Done**.

### ✅ Front → два бэка правильно

- `VITE_AUTH_API_URL` → Auth (login, me, register, …).
- Proxy `/api` → Product (catalog, cart, orders, reviews, wishlist).
- Один и тот же **access Bearer** уходит в Product после логина через Auth.

### ✅ #99–#104 — стык «покупатель ↔ отзывы ↔ Auth»

| Карточка | Решение |

Карточки **#99–#104** → **Done**. Подробности: [ОТЗЫВЫ-ПОКУПАТЕЛЕЙ.md](./ОТЗЫВЫ-ПОКУПАТЕЛЕЙ.md).

### ✅ Как Product читает личность из JWT (сейчас)

Файл `Perry.Api/Auth/AuthClaims.cs`:

- **UserId:** `NameIdentifier` → `sub` → `userId` → `uid` (первый валидный Guid).
- **Имя:** `name` → `ClaimTypes.Name` → `unique_name`.
- **Email:** `email` / `ClaimTypes.Email` / `preferred_username`.
- **Admin:** политика `RequireRole("Admin")` при `RoleClaimType=role`.

Это **толерантный** маппинг под ожидаемый контракт Auth. После ответа Влада по #98 можно сузить до одного канонического набора claims.

### ✅ CORS Product

Разрешены origins витрины/админки: `localhost:3000`, `:3001`, prod admin host и т.д.  
CORS **самого Auth** — зона Влада (нужно подтверждение для `localhost:3000`).

|-------|------------------------|-----------------|

| Role | ? (`role`?) | `User` / `Admin` |
| Email | есть в токене или только в `/api/auth/me`? | |

### ⏳ [#97](https://trello.com/c/hcmCvKWF) — plaintext credential для `local-service`

**Кто:** Влад / Auth (секрет **лично**, не в публичный канал и не в git)

**Зачем Product:**

```http
POST {Auth}/internal/auth/token
Content-Type: application/json

{ "serviceName": "local-service", "credential": "<plaintext>" }
```

→ Internal Bearer → `GET /internal/users/{id}` (permission `users.read`).

**Важно не путать:**

| Секрет | Для чего |
|--------|----------|
| `Jwt:SigningSecret` | подпись **пользовательского** access JWT (#95 ✅) |
| `InternalJwt:SigningSecret` | подпись **internal** токенов — живёт **только в Auth** |
| `CredentialHash` | хэш на стороне Auth — **не** пароль для Product |
| **plaintext credential** | то, что Product кладёт в `.env` как `AuthService__ServiceCredential` |

## 5. Целевой контракт взаимодействия (как должно быть)

### 5.1 Пользовательский поток (уже целевой)

```text
1. Front → Auth  POST /api/auth/login
2. Auth  → Front accessToken + refresh
3. Front → Product  Authorization: Bearer <accessToken>
4. Product валидирует подпись (общий HS256) + iss/aud + exp
5. Product читает UserId из claims → бизнес-данные (cart/orders/reviews)
```

Front **никогда** не шлёт `userId` как доверенное поле в body для create order/review.

### 5.2 Service-to-service (цель после #97)

```text
1. Product → Auth  POST /internal/auth/token  { serviceName, credential }
2. Auth  → Product internal accessToken (permissions)
3. Product → Auth  GET /internal/users/{id}  Bearer <internal>
4. Auth  → Product профиль (имя, email, role, status)
```

Front к Internal API **не допускается**.

### 5.3 Ошибки / здоровье (рекомендация команде)

| Сервис | Health |
|--------|--------|
| Product | `GET /api/health` ✅ |
| Auth | `GET /api/health` (+ `/api/health/database`) по [API.md](https://github.com/ITSTEP-PERRY/Backend-client/blob/main/docs/API.md) |

Желательно единый формат ошибок `{ code, message, traceId }` на следующих итерациях.

## 6. Конфиг Product (без секретов) — что смотреть ребятам

`appsettings` / `.env` (секреты только в env):

```text
Jwt__SigningSecret=<тот же, что Jwt:SigningSecret у Auth>
Jwt__Issuer=Perry.AuthService          # ждать подтверждения #96
Jwt__Audience=Perry.Client             # ждать подтверждения #96
Jwt__SkipSignatureValidation=false
Jwt__MapInboundClaims=false
Jwt__RoleClaimType=role
Jwt__NameClaimType=sub

AuthService__BaseUrl=https://perry-auth-service.orangeplant-910928aa.swedencentral.azurecontainerapps.io
AuthService__ServiceName=local-service
# AuthService__ServiceCredential=<plaintext от Влада, #97>
```

Front:

```text
VITE_AUTH_API_URL=<origin Auth Service>
# /api → Product (vite proxy :5272)
```

## 7. Smoke для проверки стыков (можно пройти на созвоне)

1. Auth `GET /api/health` → ok.  
2. Product `GET /api/health` → `{ status: Healthy, database: up }`.  
3. Login на Auth → access JWT.  
4. Decoder: выписать `iss`, `aud`, claims UserId/role/name/email → закрыть #96/#98.  
5. `GET {Product}/api/reviews/me` с Bearer → 200 (не 401).  
6. PDP → Publish review → 201, в БД `UserId` = Guid из токена.  
7. Повторный review того же товара → 409.  
8. (После #97) Product получает Internal token и `GET /internal/users/{id}` → 200.
