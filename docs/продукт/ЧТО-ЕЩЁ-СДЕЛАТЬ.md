## A. Стык Auth ↔ Product ↔ Front (P0)

Пакет на доске: **`#105`**. Без него команды спорят о «чей JWT правильный» на каждом демо.

| # | Задача | Что решает | Почему важно |
|---|--------|------------|--------------|
| **#96** | Auth: iss/aud живого access JWT | Product знает, *какой* issuer/audience принимать | Иначе 401 «на чужом» токене или ложный accept |
| **#97** | Auth: plaintext credential local-service | Product вызывает Internal Auth без догадок | Письма заказа / sync user без хардкода секретов «из головы» |
| **#98** | Auth: таблица claims access JWT | Front/Product одинаково читают `sub`, role, email | Ломается sellerId, admin-guard, «мой» заказ |
| **#106** | Auth: CORS origins для Front | Браузерный desktop/mobile web достучится до Auth | Иначе login с `:3000`/`:8081` падает на preflight |
| **#107** | Product: применить контракт после `#96`–`#98`/`#97` | Валидация JWT и Internal client совпадают с Auth | Закрывает дыру «у Auth одно, у Product другое» |
| **#108** | Front: e2e smoke Auth → Product | Доказательство стыка на живом сценарии | Защита: Register → Login → Buy без «у меня работает» |
| **#105** | Пакет «что предоставить команде» | Один чеклист для Auth/Product/Front | Снижает хаос в чате и дубли карточек |

**Владелец старта:** Auth (Влада) → затем Product → Front.
